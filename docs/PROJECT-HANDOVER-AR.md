# MicBridgeAPO — سجل التسليم الفني وخريطة المشروع

> هذا الملف مرجع تسليم للمطور أو لأي نموذج ذكاء اصطناعي سيستكمل المشروع. اقرأه قبل تعديل أي ملف.
> تاريخ إعداد هذه النسخة: 2026-11-27.
> اللغة الأساسية للمشروع: C++ وPowerShell وCMake وGitHub Actions.

## 1. الهدف الحقيقي للمشروع

MicBridgeAPO هو Windows Audio Processing Object (APO) لمعالجة صوت الميكروفون الحقيقي. لا يعتمد التصميم على ميكروفون افتراضي. يجب أن يظل الميكروفون الفعلي هو مصدر الصوت، وأن يستطيع Windows والبرامج اكتشاف استخدامه بصورة طبيعية.

معيار النجاح ليس نجاح CMake أو CI فقط. النجاح العملي يعني:
- Windows يحمل DLL ويفعّل APO على endpoint المقصود فقط.
- تطبيقات الاتصال/التسجيل ترى الميكروفون وتستطيع فتحه واستخدامه.
- مؤشرات Windows للخصوصية/استخدام الميكروفون تتصرف بصورة طبيعية.
- لا يحدث تعطيل لخدمة Windows Audio أو تغيير غير مقصود في إعدادات الصوت.
- لا تتأثر تعريفات Realtek أو أجهزة الصوت الأخرى.
- الإزالة والاسترجاع يعيدان فقط ما غيّره المثبت ويمكن إثبات ملكيته.
- التشغيل بعد التثبيت لا يحتاج اتصال إنترنت.

## 2. قواعد لا يجوز خرقها

1. لا تعدّل فرع `main`؛ يحتوي نسخة Sonnet الأصلية التي يريد المالك الاحتفاظ بها كمرجع مستقل.
2. لا تدمج أي فرع في `main` دون موافقة صريحة.
3. لا تنفذ تثبيتًا أو إزالة أو تعديلات Registry على جهاز المالك من خلال التطوير. CI يستخدم fixtures معزولة، واختبار الصوت الحقيقي ينفذه المالك يدويًا.
4. لا تلمس مفاتيح HKLM أو تسجيلات COM/APO الحقيقية في اختبارات CI. اختبارات Registry محصورة في HKCU/fixtures.
5. لا تحذف ولا تعدّل ملفات Realtek أو ملفات Windows مجهولة الملكية. الاسم أو المسار أو hash لا يثبت الملكية وحده.
6. لا تستعد backup مجهول المصدر، ولا تخمّن القيمة الأصلية لأي COM registration مشترك.
7. لا توصل Legacy cleanup executor بالمثبت قبل اكتمال أدلته واختباراته ومراجعته.
8. لا تجعل نجاح الاختبارات الأمنية الشكلية بديلًا عن الاختبار الصوتي الفعلي.
9. لا تطلب من المالك PFX أو private key أو كلمة مروره. أسرار التوقيع موجودة في GitHub Environment `release-signing`.
10. لا تنشئ tag ولا تشغّل signed release حقيقيًا دون موافقة صريحة؛ ذلك يستخدم أسرار التوقيع.
11. سياسة الشهادة: شهادة ناشر واحدة يعاد استخدامها، لا شهادة جديدة لكل build. لا تغيّر البصمة الحالية دون ضرورة وموافقة.
12. سياسة التحقق offline: لا fresh online revocation checks عند التثبيت أو التشغيل. WinTrust cache-only/no-revocation قرار مقصود، مع توثيق مخاطره وآلية تحديث البصمة عبر قناة مستقلة موثوقة.
13. لا تعتبر ملف DLL أو package صالحًا للتثبيت لمجرد أنه بُني بنجاح.

## 3. الفروع ونقاط الحفظ

### `main`
- يحتوي خط الأساس القديم الذي أنشأه Sonnet.
- لا تعدّله ولا تستبدله ولا تعِد كتابة تاريخه.
- يحتفظ به للمقارنة والرجوع إلى النسخة الأصلية.

### `recovery/provenance-from-run-1548`
- فرع التطوير الأمني/الاستردادي الذي احتوى تحسينات Manifest وReceipt وleases وBootstrap وغيرها.
- آخر نقطة CI ناجحة موثقة في سياق التسليم: run **1670**، commit:
  `269e922bbc6ece3b8f5289c65cc0f9d0353477fa`.
- run 1670 نجح في build واختبارات Windows/PowerShell والحواجز والـinvariants المذكورة في سجل المشروع.
- نجاح هذا التشغيل لا يعني أن Bootstrap صار يشغّل المثبت، ولا يعني أن APO اختُبر على جهاز Windows حقيقي.

### `rollback/provenance-run-1670`
- نسخة حفظ مستقلة أُنشئت من commit run 1670 أعلاه.
- الغرض: حفظ أحدث حالة ناجحة مع كل أعمال التطوير الموسع، كي لا تضيع عند تبسيط مسار الإصدار العملي.
- لا تستخدم هذا الفرع للتجارب اليومية؛ أنشئ فروعًا منه عند الحاجة.

### `release/practical-stability`
- فرع عمل مستقل أُنشئ من نقطة run 1670 نفسها.
- مخصص لمسار إصدار عملي محدود النطاق.
- عند إنشاء هذا المستند، هو نسخة أساس ولم يثبت بعد أنه إصدار عملي جاهز.
- لا تفترض أن كل مكونات التطوير الأمني فيه يجب أن تكون ضمن حزمة الإصدار؛ افحص الاعتماديات أولًا، ولا تحذف مكونات الحماية لمجرد تسهيل البناء.

## 4. ملخص ما أنجز عبر التطوير الموسع

### A. APO والبناء
- يوجد CMake target لبناء DLL باسم MicBridgeAPO.
- إعدادات Windows/C++17 وMSVC، مع Static CRT لتقليل اعتماد audiodg.exe على VC runtime منفصل.
- اختبارات Windows APO COM smoke ضمن CI.
- مسار البناء في workflow يستخدم `cmake -S MicBridgeAPO/MicBridgeAPO -B build -A x64`.
- يجب فحص مصدر APO الفعلي وسلوكه قبل أي تعديل؛ نجاح COM smoke لا يثبت أن Windows حمّل APO على endpoint الحقيقي.

### B. المثبت والإزالة والاسترجاع
- تطور install.ps1/uninstall.ps1 من scripts بسيطة إلى مسار أكثر حذرًا.
- أضيفت معاملات/سجلات rollback وdurable recovery journal واختبارات انقطاع واستئناف.
- أضيفت حواجز تمنع التثبيت عندما تكون بقايا النسخة القديمة أو ملكية العناصر غير محسومة.
- لا يوجد إذن عام لتنظيف كل ما يظهر في التدقيق؛ العناصر المجهولة أو المشتركة يجب أن تبقى دون مساس.
- التوافق مع النسخة القديمة المثبتة أثناء التطوير لم يُحسم تلقائيًا؛ المثبت الآمن قد يتوقف إذا لم يستطع إثبات الملكية أو baseline الأصلي.

### C. Legacy audit / cleanup planning
ملفات/وحدات مهمة تشمل:
- `MicBridge.LegacyInstallAudit.psm1`
- `MicBridge.LegacyCleanupPlan.psm1`
- `MicBridge.LegacyCleanupJournal.psm1`
- `MicBridge.LegacyCleanupPreflight.psm1`
- `MicBridge.LegacyApprovalSignature.psm1`
- `MicBridge.LegacyFileHandleLease.psm1`

ما تثبته هذه الأدوات محدود: تدقيق read-only، تصنيف المرشحات، إعداد خطة، journal، موافقة مرتبطة بالسياق، وإعادة تحقق. التدقيق لا يثبت بمفرده ملكية الملفات القديمة أو أن backup يمثل baseline الأصلي. لا يوجد تصريح بأن دورة Legacy cleanup التنفيذية مكتملة وآمنة.

### D. Manifest وإثبات المنشأ
- `MicBridge.InstallProvenanceManifest.psm1` يتحقق من CMS signature وsigner thumbprint وhashes ومجموعة الملفات، ويرفض مسارات/إضافات غير مقبولة وReparse Points.
- التحقق path-based وحده ليس ذريًا، ولا يثبت ownership أو authorization للتنفيذ.
- Receipt دائمة بعد نجاح التثبيت، مرتبطة بمعاملة التثبيت وManifest، ومحمية بـDPAPI LocalMachine وACL وatomic create/no-overwrite.
- Receipt تثبت provenance للنسخة الجديدة ولا تثبت ملكية ملفات قديمة أو COM registration مشترك.
- `MicBridge.InstallPackageFileLease.psm1` يحجز ملفات الحزمة بمقابض فعلية ويقارن المسارات/الهوية/hash، ويمنع الكتابة أو الحذف أو الاستبدال أثناء الحجز. هذا يعالج جزءًا من TOCTOU ولا يحل كل حدود الثقة بمفرده.

### E. Authenticode والتوقيع
- signed-release workflow يوقع ملفات PowerShell `.ps1` و`.psm1` قبل حساب hashes وبناء Manifest، ثم يوقع Manifest ويتحقق منه.
- يصدّر CER ويشترط تطابق SHA-1/SHA-256 وخصائص الشهادة ووجود private key وصلاحيتها.
- لا يوجد حتى run 1670 دليل على تشغيل signed release حقيقي باستخدام PFX secrets؛ workflow يعتمد على tag `v*`.
- اختبارات المقارنة test-only للبصمة لا تعادل اختبار PE موقع فعليًا بشهادة متوقعة وأخرى مختلفة.
- لا تثبّت الشهادة تلقائيًا في Windows trust stores من CI.
- ملف BAT غير موقع لا يكتسب حماية Authenticode لمجرد أن ملفات PowerShell موقعة؛ شغّل PowerShell مباشرة مع سياسة التوقيع المناسبة عند اعتماد الحزمة.

### F. Bootstrap
- أضيف تصميم ومكوّن C++ مستقل باسم MicBridgeBootstrap.
- يوجد WinVerifyTrust/pinned signer verifier منفصل.
- المشغّل الحالي scaffold fail-closed ويرفض الاستمرار برمز خروج 78؛ لم يكتمل ربطه بالـverifier.
- لا يتحقق بعد من Manifest/CMS وكل ملفات PowerShell، ولا ينشئ handoff موثوقًا إلى المثبت.
- `BootstrapTrustEstablished=false` حاجز مقصود. لا تغيّره لتجاوز الحظر.
- لذلك التثبيت عبر المسار الآمن المتقدم غير جاهز حاليًا حتى يكتمل Bootstrap. لا تدّع أن وجود الملف التنفيذي وحده يكفي.

## 6. المشكلة التشغيلية الأصلية التي يجب ألا تضيع

سبق أن جُرّبت نسخة أثناء التطوير، وكانت المشكلة:
- Windows لم يستدعِ/يحمّل DLL كما كان متوقعًا.
- لم يظهر للبرنامج/النظام أن الميكروفون مستخدم من تطبيق.
- فُحص السلوك في Process Monitor.
لا يوجد في السجل المتاح إثبات أن إصدار run 1670 أصلح هذه المشكلة. يجب عدم افتراض ذلك من CI.

### اختبار القبول العملي على جهاز المالك
يُجرى بعد تجهيز حزمة مرشحة آمنة، وبموافقة المالك:
1. تسجيل حالة أجهزة الإدخال وتعريفاتها وإعداداتها قبل الاختبار (قراءة فقط).
2. التأكد من endpoint المقصود والـAPO registration والـCLSID ونسخة DLL التي ستُحمّل.
3. تشغيل أداة/تطبيق يسجل صوت الميكروفون الحقيقي، ثم مراقبة Windows microphone-use indicator وفتح الجهاز.
4. استخدام Process Monitor بمرشحات واضحة للتحقق من تحميل DLL من المسار الصحيح بواسطة مكونات Windows Audio، مع التقاط Result/Process/Path. لا تستنتج أن عدم ظهور DLL وحده دليل قاطع قبل ضبط الفلاتر والتوقيت.
5. تجربة تطبيقين معروفين يستخدمان الميكروفون، والتحقق من استمرار عمل الميكروفون ومؤشر الاستخدام.
6. التحقق من عدم تغير أجهزة Realtek أو أجهزة الإدخال الأخرى أو خدمة Windows Audio.
7. اختبار الإزالة/الاسترجاع فقط بعد حفظ baseline موثوق ومراجعة ما سيُغيّر؛ لا تُجرّب الإزالة على حالة مجهولة.
8. إذا تعذر تحميل APO أو ظهرت آثار جانبية، أوقف التجربة ولا تكرر التثبيت/الإزالة عشوائيًا. اجمع logs وProcmon trace أولًا.

## 7. مسار الإصدار العملي المقترح — نطاق محدود

الهدف هو تقليل الوقت دون تجاوز حواجز سلامة Windows:
1. افحص CMake والـAPO source وinstaller في فرع `release/practical-stability` لتحديد أصغر dependency set قابلة للبناء.
2. لا تعِد كتابة APO أو تغيّر DSP ما لم تثبت الحاجة.
3. افصل مكونات Manifest/Bootstrap غير المكتملة عن مسار الإصدار العملي فقط إذا أمكن توفير بديل موثوق للتحقق من الحزمة وعدم تشغيل كود غير موثوق. لا تجعل bypass أو تعطيل التحقق حلًا.
4. إن لم يتوفر bootstrap آمن مختصر، لا تصدر installer قابلًا للتنفيذ بصمت؛ جهّز package تشخيصية/اختبارية غير مثبتة أو أكمل أصغر bootstrap آمن.
5. لا تعدّل تسجيلات HKLM أو ملفات النظام في CI.
6. بعد كل تغيير، ابنِ على GitHub وشغّل اختبارات CI المتاحة، ثم افحص artifact ومحتوياته.
7. بعد نجاح CI، أوقف التطوير وسلم الحزمة للمالك للاختبار العملي. لا تعتبرها مستقرة نهائيًا قبل اختبار تحميل APO واستخدام الميكروفون.
8. لا تنشئ release tag ولا تستخدم PFX secrets إلا بعد موافقة المالك.

## 8. ما تبقى للتطوير الموسع (يمكن تأجيله)

- اختبارات Authenticode PE فعلية لقبول signer المتوقع ورفض signer آخر، وunsigned/invalid signatures، مع التأكد من إغلاق WinTrust state.
- ربط MicBridgeBootstrap بالتحقق من Authenticode وManifest/CMS وملفات PowerShell.
- قناة handoff موثوقة بين Bootstrap والمثبت تمنع تشغيل install.ps1 مباشرة.
- إثبات أن الملفات المستخدمة هي نفسها الملفات التي جرى التحقق منها، مع اختبارات concurrency/TOCTOU شاملة.
- اختبار end-to-end للحزمة حتى Receipt مع حالات tampering/failure/recovery.
- تصميم واختبار timestamping والتحقق التاريخي بعد 2031.
- استكمال دورة Legacy ownership/provenance/approval/lease/execute/final verify، دون المساس بالعناصر مجهولة الملكية.

## 9. خريطة الملفات المهمة

المسارات التالية داخل مجلد المشروع `MicBridgeAPO/MicBridgeAPO/`:
- `CMakeLists.txt`: أهداف البناء واختبارات CMake/CTest.
- `src/`: تنفيذ APO وملفات التصدير؛ نقطة البداية لفهم تحميل APO وسلوكه الصوتي.
- `install.ps1`: منطق التثبيت والتحقق والرفع والصلاحيات والتسجيل.
- `uninstall.ps1`: منطق الإزالة والاسترجاع؛ لا تفترض أن كل عنصر يمكن حذفه.
- `tools/`: وحدات PowerShell لاختبارات التسجيل والـjournals والـManifest والـleases والـReceipt والتدقيق.
- `.github/workflows/build.yml`: CI للبناء والاختبارات.
- `.github/workflows/signed-release.yml`: workflow توقيع الإصدارات؛ لا تشغله دون موافقة.
- `docs/BOOTSTRAP-LAUNCHER-SECURITY-DESIGN.md`: التصميم الأمني للمشغّل وحدوده الحالية.

للتعرّف على التنفيذ الدقيق، اقرأ الملفات الفعلية في الفرع المطلوب؛ لا تعتمد على هذا الملخص بدل الكود أو سجلات CI. أسماء الملفات قد تختلف بين main وفروع التطوير.

## 10. تعليمات للمطور/نموذج الذكاء الاصطناعي التالي

ابدأ بقراءة هذا الملف ثم:
1. تحقق من branch وHEAD وworkflow run المرتبط به قبل أي تعديل.
2. اقرأ CMake وAPO source وinstaller وuninstaller والاختبارات ذات الصلة.
3. افصل بين ثلاثة أنواع من الإثبات: build/CI، سلامة التوقيع والمنشأ، والسلوك الحقيقي على جهاز Windows.
4. لا تقل إن الميكروفون يعمل أو إن Windows آمن قبل الاختبار العملي.
5. نفّذ تغييرًا صغيرًا واحدًا في كل مرة، راقب CI، أصلح السبب الجذري للفشل، ثم تحقق من آخر commit.
6. لا تمس main ولا rollback.
7. بعد إكمال محطة، اعرض commit وrun والنتائج والفجوات وتوقف بانتظار طلب المتابعة.

**الحالة النهائية عند كتابة هذا الملف:** لدينا نقطة تطوير موسعة محفوظة وCI ناجح عند run 1670، لكن لم يثبت بعد أن المشكلة التشغيلية الأصلية الخاصة بتحميل DLL واكتشاف استخدام الميكروفون قد حُلّت. كما أن Bootstrap الأمني غير مكتمل. لا توجد حاليًا قاعدة كافية لوصف أي حزمة من هذا الفرع بأنها جاهزة للتثبيت النهائي.
